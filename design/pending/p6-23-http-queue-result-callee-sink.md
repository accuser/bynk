## ADR: http-queue-result-callee-sink

title: `Callee::Intrinsic` now covers `HttpResult`/`QueueResult` bare-variant construction — the sink Decision C's own exclusion said a future slice would need

summary: Closes the checker-side half of the gap this track's own P6.21/P6.23 investigations both independently found — no `Callee` classification existed for `HttpResult`/`QueueResult` variant construction at all, forcing the emitter's own dispatchers to keep re-deriving it from bare names

**Context.** `bynk-emit::ir::lower`'s own `GlobalRef` (P6.1, Decision C) explicitly named `HttpResult`/`QueueResult` bare-variant references as originally in scope, then dropped during implementation — its own doc comment gives the reason: the checker's disambiguation for these names is *contextual*, not structural. A bare `NotFound` resolves to `HttpResult.NotFound` only when the surrounding type implies it, or when no user-declared sum type owns a variant of the same name — `expected`/`ctx.return_ty` peeling the checker already does, but never recorded anywhere a later reader (an IR lowering pass, or — this session's own finding — `emitter/lower.rs`'s own string-emitting dispatchers) could read back without re-running the identical contextual logic itself, the exact duplication the whole `Callee` precedent (P6.0) exists to avoid.

Two independent investigations this session hit the same wall from different directions: a P6.21 scoping pass found `lower_method_call`'s own `HttpResult` branches are still 100% name-matched (`id.name == HTTP_RESULT`) with no `Callee` to read; P6.23's own safety probe found `lower_service_item_ir` panics on 27 of its ~51 real-corpus failures with the exact message "no `Callee` recorded for this call... one of the shapes Decision C left out on purpose."

**Decision.** Add the missing sink at all 8 real dispatch sites in `checker.rs`'s own `type_of` (the only function that ever resolves `http_variant`/`queue_variant`): bare `Ident` (both `HttpResult` and `QueueResult`), `Call` (both), `ConstructorCall` — `HttpResult.X(...)`/`QueueResult.X(...)` qualified-with-args form (both), `FieldAccess` — `HttpResult.X` qualified nullary form (`HttpResult` only; no bare-nullary-qualified `QueueResult` form exists in the grammar), and `MethodCall` — the qualified-with-args form reached through method-call syntax (`HttpResult` only; the equivalent `QueueResult` case isn't reachable through this AST shape). Each insertion mirrors the exact pattern the sibling `StoreField::Cell` arm (a few lines below the `MethodCall` site) already established: `ctx.callees.insert(expr.id, Callee::Intrinsic { ns: HTTP_RESULT | QUEUE_RESULT, op: variant.name.to_string() })`, reusing `Callee::Intrinsic` rather than adding a new variant — `HttpResult`/`QueueResult` variant construction is exactly what that variant's own doc comment describes ("a built-in static constructor with no declaring type"), the same shape `List.empty`/`Bytes.fromUtf8`/etc. already use.

**Purely additive, by construction.** Every insertion happens only inside a branch that was already resolved to construct the variant — no new branch, no changed control flow, no changed diagnostic. Nothing in `bynk-emit` reads `Callee::Intrinsic` for `ns: HTTP_RESULT`/`QUEUE_RESULT` yet (that's the emitter-side follow-up this PR sets up, not this PR itself), so this change cannot alter any generated output today.

**Consequences.** Verified by the full `bynk-check` unit test suite (157/157, unchanged) and a full zero-diff bless against the entire `bynkc` e2e fixture corpus — confirming the additive-only claim empirically, not just by inspection. This is the sink `GlobalRef`'s own doc comment said a future slice would need to add "or accept re-deriving it" — the first option is now real. Unblocks, as a real follow-up (not this PR): `lower_method_call`/`lower_call`'s own remaining `HttpResult`/`QueueResult` branches (the last piece of P6.21's incremental conversion), and most of P6.23's own 5 root causes (27 of ~51 corpus panics were exactly this gap).
