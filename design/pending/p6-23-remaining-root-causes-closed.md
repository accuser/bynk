## ADR: remaining-root-causes-closed

title: `lower_service_item_ir` now lowers every real service body in the fixture corpus cleanly — P6.23's safety probe reaches zero

summary: Root-causes and fixes the two remaining panic classes the P6.23 safety investigation found, both narrow, real bugs rather than design questions — completing the safety-verification work this track's own completion plan called for before wiring `IrItem::Service` into any real consumer

**Context.** After #1251/#1252/#1253 closed the `HttpResult`/`QueueResult` gap (the dominant root cause, ~46 of ~51 original panics), re-running the P6.23 safety probe (`lower_service_item_ir` wrapped in `catch_unwind` across every real service in the `bynkc` e2e corpus) found the panic count down to 5, all inside one unit (`commerce.order`/`markPaid`) — plus a separate, previously-uncounted panic surfaced once the dominant class stopped masking it (`demo`/`Api`, `1199_service_handler_unresolvable_param_type_no_ice`). Both root-caused directly against their own real fixtures rather than assumed.

**Bug 1 — the wrong signature function.** `lower_service_handler_ir` (`ir/lower.rs`) called `lower_handler_signature_ir` — the *agent*-oriented signature reader, which panics on a resolve miss because the checker genuinely does guarantee an agent handler's own param type resolves. But `1199_service_handler_unresolvable_param_type_no_ice` exists specifically to pin the opposite fact for a *service* handler: `check_http_handler` validates a param's name only, never its declared type, so an undeclared param type (`Nope`) certifies. `lower_service_handler_signature_ir` — this function's own real sibling, sitting one function away — was already graceful (`cx.unit_ty()` on a miss) *since it was written*; this call site was simply never updated to use it. Swapped. `lower_service_handler_body_ir`'s own param-binding loop carried the identical panic independently (a second, un-synced copy of the same resolve-and-bind logic) and is fixed the same way, matching its own signature-only sibling.

**Bug 2 — qualified nullary variant construction misread as field access.** `Region.International` parses as `ExprKind::FieldAccess { receiver: Region, field: International }`. The checker's own `check_field_access` (`expressions.rs`) has a dedicated branch for this exact shape — a bare-`Ident` receiver naming a declared sum type that owns a variant tagged `field.name` — and it returns the variant's own constructed type *directly*, via `nullary_variant_ty`, without ever calling `type_of(receiver, ...)` on the receiver first. So `Region`'s own `ExprId` — used purely as a namespace qualifier here, never as a value — never gets an `expr_types` entry. `lower_expr_ir`'s own `FieldAccess` arm unconditionally recursed into `lower_expr_ir(receiver, cx)`, hitting `cx.expr_ty(receiver.id)`'s own ADR 0334 "no recorded type" guard. Fixed by mirroring the checker's own dispatch (same `cx.lookup(...).is_none()` shadowing guard) before falling through to ordinary field access: if `receiver` bare-names a declared sum type with a matching variant, produce `IrExprKind::Variant { tag, payload: [] }` directly, the same node `lower_call_ir`'s own `Callee::Ctor` arm already produces for the identical construction reached through a `Call`/`ConstructorCall` shape — this is the `FieldAccess`-reached third form of the same thing.

**Consequences.** `lower_service_item_ir`'s own panic count is now zero across the entire e2e fixture corpus — down from ~51 across 20 services when the P6.23 safety investigation first ran. This is real, measured completion of the plan's own "verify empirically" risk item for wiring a real `IrItem::Service` consumer — the architecture was already sound (confirmed earlier), and now the body-lowering path it depends on is too. No shipped emitter path reaches `lower_service_item_ir` yet — this stays dormant, same posture as every other P6.x IR-pass fix; P6.23 itself (re-routing `EventSubscriberShape`) and P6.22 (an `IrExpr`-based walk) remain separate, not-yet-scoped slices, but neither is blocked on an unknown safety gap anymore. Verified by the full `ir::` unit test suite (133/133, two new tests pinning both fixes directly against their own real-corpus shapes) and a full zero-diff bless against the entire e2e fixture corpus.
