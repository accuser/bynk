## ADR: uses-reaches-hidden-types
title: An imported declaration's types resolve in its declaring scope; a type reached only that way is resolvable but not nameable
summary: close_reachable_types adds the types imported declarations reach as hidden types; a naming gate keeps uses one level for naming

**Context.** `uses` is one level, by design ([[0277]], [[0278]]): a unit names the types its `uses` targets declare, not theirs. But a unit's composed table (`compose_unit_symbols`) was also its only table for *resolution*, and the checker resolved an imported declaration's types against it. A type the declaration reached through its own `uses` was absent, resolved to nothing, and a missing type is permissive. So every position it typed went unchecked: a record literal's field, a field read, an imported fn's return, a method's signature, and the same through a consumed context's export. The emitter then branded nothing, so `tsc` rejected output that `bynkc check` had passed (#1807, found after #1778).

**Decision.** Resolution follows the declaration and naming follows `uses`.
- `close_reachable_types` runs after `uses` and `consumes` are merged. It resolves each type that an imported type body, fn signature or method signature names, in that declaration's own scope (its unit's types, then its unit's `uses`, the same precedence a unit gives its own names). It repeats this for each type it adds. A reached type the table lacks is added with its owning commons as provenance, together with its methods, and is recorded as *hidden*. A reached type that a context owns is not added: it can only arrive through a consumed export, so that is an `exports` question.
- A naming gate (`check_hidden_type_names`) runs beside the resolver in both build and analyse modes. It rejects a hidden name written anywhere a type name is written, as `bynk.resolve.unknown_type`, the error the name gave before, now with a note to `uses` its commons. A refinement test (`s is Repo`) names its type, so it is gated too. A bare variant of a hidden sum is a value, not a type name, so it isn't: a commons builds `Job { status: Pending }` and either kind of unit matches on `Pending`, typed by the position it fills, the way a literal is admitted as a hidden refined type. A context still can't build the variant, because #907's rebrand-construction rule (`bynk.context.rebrand_construction`) covers a hidden commons sum just as it covers a directly used one.
- If the reached name is already bound to a different unit's declaration, that's `bynk.uses.name_conflict`, unless the unit `uses` the reached type's commons directly. Shadowing a directly used type keeps its existing meaning: `1697_derived_names_collide` declares its own `Message` beside `uses bynk.locale.types`.
- Emission imports a hidden type from its owning commons file and, in a context, rebrands it and forwards its methods. Both happen only when the module spells the type (#1805's `settle_implied`).

**Consequences.** Programs that relied on the hole stop compiling. That's a break for a pre-1.0 `minor`, but each such program was ill-typed, and none in this repository was. A program with no ill-typed position is unchanged. Every existing golden is byte-identical, `62_uses_chain` and `65_money_uses_time` included. Rejected: requiring a direct `uses` of the reached commons wherever a reached type is touched. That would break correct programs that compile today (`fn read(r: Run) -> String { r.repo }`), and `62_uses_chain` pins that declaring across a chain is legal. Known gaps: unit and integration suites compose their own one-level views, so a suite still has the hole. Editor completion may list a hidden type. A `workers` commons codec for a field typed by a used commons's refined type calls an unimported codec, on `main` and here alike. One positive fixture and nine negatives pin the change, and a mutation of each mechanism (the closure, the gate, the conflict, hidden methods, decl paths and method forwarders) fails at least one of them.
