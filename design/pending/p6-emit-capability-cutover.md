changelog: P6.x cutover slice 3 (design/tracks/the-ir.md §5/§6, #1193, #1187, narrowed — Provider deferred) — emit_capability now reads each capability op's resolved params/return type off OpSig (bynk-emit::ir, built by lower_capability_item_ir/lower_op_sig_ir) through ts_ty, instead of walking CapabilityOp::params/return_type TypeRefs through ts_type_ref directly. emit_capability gains new ops (&[OpSig]) and commons (&TypedCommons) parameters (c (&CapabilityDecl) stays too — IrItem::Capability::def is a bare String, carrying neither documentation nor an Arc back to the declaration); its one call site (emitter.rs's emit_project) lowers the IrItem::Capability inline, no new helper (a single caller doesn't earn one, unlike type_shape_for's three). Provider is deliberately not converted in this slice — despite #1187's own pairing — because a ProviderOp always carries a real body, and lower_provider_op_ir routes it through lower_expr_ir, which still hits #1189's open comparison/arithmetic BinOp gap; Capability ops are signature-only, no body, so no such surface exists. ast_importers does not move (emit.rs stays invisible to the probe, same as slice 1). One accepted, narrow behaviour difference — a capability op whose param/return type name the checker never validates (already-accepted-but-nonsensical today) rendered as its raw undefined name before this slice and renders as void after, since lower_op_sig_ir's own resolve-or-Unit fallback mirrors the checker's own pre-existing leniency (context_checks::build_capability_op_info) — no valid program can reach this. No other author-facing behaviour change; differential tests (bynk-emit/src/emitter/emit.rs, capability_op_sig_emission_tests) cover a multi-op capability, a named param/return type, and — new relative to the prior IrItem::Type/Fn cutover slices' own corpus — a generic op's own rigid type variable, through the project emission pipeline (capability is a context-only construct, so it never reaches the single-file emit() path)
