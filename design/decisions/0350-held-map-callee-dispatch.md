# 0350 — `lower_method_call`'s held-`Map[K, Connection]` branch reads `Callee::Store`/`Callee::Query` instead of `!cx.is_local`

- **Status:** Accepted (v0.249.2)

summary: Closes another of `lower_method_call`'s remaining name-matched-receiver branches, following the same pattern already applied to ordinary storage, agent-method, constructor, and `Events.emit` dispatch

**Context.** `lower_method_call`'s held-`store Map[K, Connection]` branch (real-time track slice 3b, v0.104/v0.105) detected its own receiver with `!cx.is_local(&id.name)` — a check that only rules out a *local* binding sharing the field's name, not any other value that happens to share it, and not immune to the general shadowing concern R6.5 names. Every other branch in this module already converted by P6.21 reads the checker's own `Callee` classification instead.

`store_ops.rs`'s own doc comment confirms a held `Map[K, Connection]` field's method calls resolve through the identical `StoreField::Map` checker dispatch as an ordinary storage map — entry ops (`put`/`remove`/`contains`/`size`/`get`) are classified `Callee::Store`, and the vocabulary that `is_query_op` lifts (e.g. `parTraverse`) is classified `Callee::Query` — only query *accessors* (`.entries`/`.keys`/`.values`) are statically rejected on a held map, a separate rule (`bynk.held.query_accessor_on_held_map`) unrelated to which `Callee` a method call itself resolves to.

**Decision.** Replace `!cx.is_local(&id.name)` with `matches!(cx.commons().callee(e.id), Some(Callee::Store { .. } | Callee::Query { .. }))`, mirroring the ordinary (non-held) Map branch's own guard immediately below it. `agent_held_map_frame(&id.name)` stays unchanged as the side-table lookup that decides *which* store-field kind this is (held vs ordinary) — a different question than the one `Callee` settles.

**A real regression, caught before landing.** The first attempt matched `Callee::Store` only. Zero-diff bless caught a real diff in `238_websocket_inbound_workers`'s expected output: `conns.parTraverse(...)` (a lifted query op, `Callee::Query`, not `Callee::Store`) fell through the now-too-narrow guard, landing instead on a later generic query-kernel fallthrough that independently re-lowered the receiver and wrapped it in a redundant invoked closure — semantically equivalent JS, but a real diff. Fixed by matching both `Callee` variants; re-verified zero-diff, including that exact fixture.

**Consequences.** Verified by a full zero-diff bless against the entire `bynkc` e2e fixture corpus, including every held-map fixture in the corpus (`235_held_connection`, `238_websocket_inbound_workers`, `340_ws_broadcast_try`, `338_ws_broadcast_collect_all`). `ast_importers` unaffected. The `Ty`-keyed kernel-method fallthrough remains `lower_method_call`'s one still-unconverted receiver-detection path — it dispatches on the receiver's own checked type already, not a name match, and is not suspected to carry the same defect (unexamined, lower priority per the track doc's own prior findings).
