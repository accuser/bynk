# 0444 — A stub's injected fault is a fault, and a case observes it with `expect <call> faults`

- **Status:** Accepted (v0.313)

**Context.** [[0152]] made observation a sugar on `expect`, and the `stub` clause added `fails` to inject a capability fault at a seam. The emitted stub throws `bynk: injected capability fault (stubs … fails)`. That exception propagates out of the handler and out of the case, so the case fails before its next `expect` runs. Four documents disagreed with this. The testing reference and the testing guide both titled an example "a fault surfaces as an error" and asserted `expect r is Err(_)` after a `fails` stub. The runtime-library spec said the fault "the seam propagates as an `Err`", and the emission spec lowered `fails` to "a thrown/`Err` capability fault". The rest of the language treats a fault as untyped and uncatchable: an invariant violation is a fault the caller cannot handle, and a faulting handler commits nothing. No `expect` form could observe a fault, so `fails` was useful only as the first outcome of a `returns each` sequence (#1706).

**Decision.** A fault is a fault. `fails` throws, exactly as a real provider's failure would, and never surfaces as an `Err`; the four documents now say so. A case observes a fault with a new `expect` subject, `expect <call> faults`. It awaits the call and holds when the call throws, whatever the thrown value. A fault is untyped, so the claim cannot discriminate. The one exception is the case's own `ExpectationError`: a failed `expect` raised while the call is evaluated is the case failing, not the call faulting, and propagates. `faults` is a contextual word, an ordinary identifier everywhere else, like the observation words. The subject must be a call expression of type `Effect[_]` (`bynk.expect.faults_not_effect`). A test-body binding from an address call is deliberately untyped, so the syntactic test is what rejects `expect r faults` on a value already bound. The claim has no `by` slot, so an identity-carrying handler is reported as for an absent `by`. It is not allowed in a `system`-tier case (`bynk.test.faults_needs_in_process`), where a handler's fault crosses the deployed Worker as an error response and never reaches the harness as a throw.

**Consequences.** The claim is a test's observation of a fault, not a handler for one: it exists only in a `case`, and production code still cannot catch a fault. Rejected: making a fault surface as an `Err` (option 2 in #1706). That works only when the handler returns a `Result`, and it would require the seam to know its caller's error type, contradicting faults being untyped everywhere else. Rejected: a case-level "this case faults" marker. It cannot say *which* call faults, nor combine with a later `returns each` success in the same case, which the statement form does. A `system`-tier fault claim, and a `by` clause on the claim, are left open; a case at `system` asserts the error response instead. A behavioural fixture pins all four outcomes at runtime: a `fails` stub satisfies the claim, a sequence serves a fault then a value, a returning call fails the claim, and an unclaimed fault fails its case.
