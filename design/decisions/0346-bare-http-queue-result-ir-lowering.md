# 0346 — `lower_ident_ir` lowers a bare `HttpResult`/`QueueResult` nullary variant to a real `IrExprKind::Call` — the bare-value sibling of P6.20-pre's own store-field fix

- **Status:** Accepted (v0.248.14)

summary: Closes the last of the shapes `GlobalRef`'s own doc comment named as dropped from Decision C's scope for lack of a sink — now real via #1251's `Callee::Intrinsic` — and measurably shrinks P6.23's own remaining safety gap from ~51 panics across 20 services to 5 across 1

**Context.** #1251/#1252 gave the checker and the string-emitting `emitter/lower.rs` a real `Callee::Intrinsic` classification for `HttpResult`/`QueueResult` variant construction. `bynk-emit::ir::lower`'s own `lower_ident_ir` — the *other* lowering pass, dormant but exercised by P6.23's own safety probe against `lower_service_item_ir` — still panicked on the bare-nullary form (`Ack`, `NotFound`) via its final defensive `todo!()`, the exact shape `GlobalRef`'s own doc comment (P6.1, Decision C) named as originally in scope, then dropped for lack of a sink.

**Decision.** `lower_ident_ir` gained a new `expr_id: Option<ExprId>` parameter — `Some(e.id)` at its one real call site (`lower_expr_ir`'s own `ExprKind::Ident` arm, which always has a genuine `Expr`/`ExprId`), `None` at its two shorthand-record-field call sites (`{ x }` — the parser never builds an `Expr`/`ExprId` for the shorthand name itself, and both call sites already assert `cx.lookup` must succeed, so a `Callee` lookup there would never fire regardless). A new check, placed right after the existing `store_queryable` check: if `expr_id` resolves to a `Callee::Intrinsic` (via `cx.callee(id)`), wrap it as `IrExprKind::Call { callee, targs: vec![], args: vec![] }` — the identical shape `lower_call_ir` already produces for the call-with-args sibling (`Retry(reason)`), so both forms of the same variant share one representation. Unlike `store_queryable`'s own name-based lookup (which needed careful ordering to avoid re-deriving an ambiguous match), this check is keyed by the expression's own `ExprId` — the checker already decided, once, whether *this specific expression* is this shape, so there is no shadowing/precedence question its position in the ladder could get wrong.

**A pre-existing test's own proof technique relied on this exact bug as a signal.** `a_queue_services_on_message_handler_reaches_ordinary_body_lowering_not_the_websocket_deferral` proved a queue `on message` handler reaches ordinary body lowering (rather than being caught by the WebSocket-specific deferral gate, since `HandlerKind::Message` is shared between the two protocols) by asserting the body panicked on this exact `Ack` gap, deliberately, rather than on a WebSocket-specific message. Now that the gap is closed, the test asserts the same property directly: `connection.is_none()` (only a `from websocket` lifecycle handler ever gets one), and the body actually lowers to `IrExprKind::Call { callee: Callee::Intrinsic { ns: QUEUE_RESULT, op: "Ack" }, args: [] }`.

**Consequences.** No shipped emitter path reaches `lower_service_item_ir`/`lower_ident_ir` in production yet — this stays dormant, same posture as every other P6.x IR-pass fix. Verified by the full `ir::` unit test suite (131/131) and a full zero-diff bless against the entire e2e fixture corpus (the change is IR-pass-only, so zero-diff is expected by construction, not just observed). Re-running the P6.23 safety probe (`lower_service_item_ir` wrapped in `catch_unwind` across every real service in the corpus) after this fix, on top of #1251/#1252, found the panic count drop from ~51 across 20 distinct services to **5, all inside one unit** (`commerce.order`/`markPaid`) — the two remaining root causes (a genuine ADR 0334 checker/IR-lowering type-disagreement, and a handler-param resolve-miss) are real, narrow bugs, not design questions, and are left for their own follow-up investigation.
