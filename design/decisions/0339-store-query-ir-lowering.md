# 0339 — A bare `store Map`/`store Log` field used as a value gets its own `IrExprKind::StoreQuery`, not a widened `Local` binding

- **Status:** Accepted (v0.248.7)

summary: Closes a real gap the completion plan for #1137 flagged as unverified before P6.20 — found empirically via a direct panic probe over the full fixture corpus, not assumed from the plan's own optimistic dependency graph

**Context.** The completion plan for #1137 ordered P6.20 (a real `IrItem::Agent`/`Provider` enumerator in `project.rs`) behind P6.15/P6.16 (`Question`/`Is`), with an explicit caveat: "verify empirically, before P6.20, that real fixture-corpus provider/agent bodies don't also hit `lower_ident_ir`'s other fallback `todo!()`s... beyond `Question`/`Is`." With both landed, that verification was run directly — a `catch_unwind` probe wrapping `lower_agent_item_ir`/`lower_provider_item_ir` over every real `CommonsItem::Agent`/`Provider` in the full `bynkc` e2e fixture corpus. It found 4 real panics, all the same root cause: a bare `store Map`/`store Log` field name used as a **value**, not a method-call receiver — `Sales`/`orders` (`231_query_joins`, `lines.joinOn(orders, ...)`, an argument-position reference), `Inventory`/`items` and `Ledger`/`balances` (`353_map_entries_query`, `items.entries`/`.keys`/`.values`, a `FieldAccess`-receiver-position reference).

Both shapes reduce to the same underlying gap: `lower_handler_body_ir` only ever bound `Cell` store fields into `LowerIrCtx`'s ordinary `scopes` (v0.81's "implicit deref in read position" rule) — a `Map`/`Log` field was never bound at all, so a bare reference to one fell through `lower_ident_ir`'s classification ladder straight into its own defensive `todo!()`, previously believed structurally unreachable through a real handler body.

**Decision.** Widening the existing `Cell`-only binding to cover every store-field kind is the wrong fix: `StoreField`'s own doc comment is explicit that "storage kinds are not value types" — a `Map` field has no ordinary `TyId` to bind as a `Local` the way a `Cell`'s element type does. The checker's own `ExprKind::Ident` dispatch (`checker.rs:3477-3481`, ADR 0120) already draws this line: a bare `Map` field not shadowed by a local types as `Ty::Query(V)` through a **dedicated dispatch checked before `check_ident`**, never entering the ordinary value scope at all. This slice mirrors that structure rather than re-deriving it:

1. A new `LowerIrCtx.store_queryable: HashSet<String>` — a second table, parallel to (not merged into) `scopes`, set once by `lower_handler_body_ir` via a new `set_store_queryable` (mirroring `set_return_ty`'s own "set once by the one real entry point that needs it" shape). Computed once per agent in `lower_agent_item_ir`, from `state`'s own already-lowered `StoreFieldIr::kind`, filtering `Map` — the same "derive from what's already lowered, don't re-resolve" discipline `store_cells` itself already established.
2. A new `IrExprKind::StoreQuery(String)`, checked in `lower_ident_ir`'s ladder immediately after the existing `cx.lookup` guard — matching the checker's precedence exactly (`ctx.lookup(...).is_none() && ...` returns before `check_ident`, where a free-fn reference or nullary variant resolve, ever sees the name). Carries only the field's own name: every consumer already has the enclosing `IrItem::Agent`'s `state: Vec<StoreFieldIr>` to resolve the kind back through, the same "identity, not a copy" posture `Callee::Store::field`/`GlobalRef::tag` already established.
3. **`Set`/`Cache`/`Log` fields are deliberately excluded from `store_queryable`.** The checker's own dispatch only special-cases `Map` for a bare-value reference — a bare `Set`/`Cache`/`Log` field is not checker-legal there at all (`bynk.resolve.unknown_name` on a certified program), so leaving them out and falling through to `lower_ident_ir`'s existing `todo!()` is correct: structurally unreachable, not merely unhandled, the same distinction this module's own doc comments draw everywhere else. `Log` was wrongly included in this slice's own first draft — the shipped emitter's `is_agent_store_log` (`emitter/lower.rs:4117`, "v0.95 ADR 0121") suggested it belonged alongside `Map`, but `bynk-check` never actually special-cases `StoreField::Log` in a bare-value or `.entries`/`.keys`/`.values` dispatch the way it does `StoreField::Map` — every other `StoreField::Log` site in `bynk-check` is an unrelated `:=`-target check, a method dispatch, or the table build. Caught by review before merge.
4. **Invariants deliberately do not get `store_queryable`.** `lower_invariant_ir` is handed only `store_cells` (mirroring `check_invariants`, `context_checks.rs:2955`, which is handed only `store_cells` too) — a bare `Map` reference inside an invariant predicate is not checker-legal, so this asymmetry with `lower_handler_ir` is intentional, not an oversight.

No new logic was needed for the `.entries`/`.keys`/`.values` `FieldAccess` shape specifically: `ExprKind::FieldAccess`'s own lowering always lowers its `receiver` unconditionally through the ordinary `lower_expr_ir`/`lower_ident_ir` path, so fixing the bare-ident dispatch fixes both AST shapes at once — confirmed by re-running the same panic probe against the full e2e corpus afterward and finding zero remaining panics.

**Consequences.** No shipped emitter path reaches `IrExprKind::StoreQuery` yet (same dormant posture as `Question`/`Is`, P6.15/P6.16) — a future consumer decides how `Field { base: StoreQuery(_), field: "entries"|"keys"|"values" }` renders, not this slice. Verified by four unit tests against the shared `Ledger` handler fixture: the two real AST shapes found in the corpus (a `.keys` `FieldAccess` receiver, a bare argument to a `Query`-typed free-function parameter), plus two review-driven pins (a local param shadowing the store field's own name resolves to `Local`; a free fn colliding with the store field's own name still resolves to `StoreQuery`, not the free-fn `todo!()`) — all asserting the underlying node directly rather than trusting a full-body snapshot. Zero-diff bless confirmed regardless. This closes the plan's own unresolved "verify empirically before P6.20" risk item — P6.20 itself remains a separate, not-yet-started slice, but is no longer blocked on an unknown safety gap.

**Review of #1240 found two real issues, both fixed before merge (not left for a follow-up PR, since the PR had not yet merged when review landed):** the dispatch-ordering bug and the `Log` misclassification, both described in points 2 and 3 above.
